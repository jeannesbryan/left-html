The quiet cost of a shared dependency

March 3, 2026 ·6 min read ·Essays ·Jeannes Bryan

infrastructure privacy

Every dependency you do not control is a decision somebody else gets to make later, on your behalf, without asking. That is not an argument against dependencies — it is an argument for knowing which ones you have taken.

The bill arrives quietly, and it is usually denominated in afternoons.

What it looks like when it comes due

A stylesheet URL that names a version it no longer serves. A build that only works on one machine. A dependency that publishes a breaking change on a Tuesday. None of these announce themselves; you find out when something upstream moves and a page you did not touch starts rendering wrong.

The three questions worth asking

  • Can I read the whole thing? If the source is not available, the dependency is a black box with a renewal date.
  • What happens if it disappears? A vendored copy survives an upstream disappearance. A CDN link does not.
  • Who updates it, and how would I know? An unowned dependency is not stable; it is frozen and drifting.
Nothing is as expensive as a mistake that looked obvious only afterwards.

Vendoring is not the same as never updating

Keeping a local copy buys you the ability to decide when to move, which is the only thing that makes an upgrade safe to attempt. It does not remove the obligation to move eventually.

# the copy is the thing you actually ship
cp -p vendor/reset.css assets/reset.css
md5sum assets/reset.css

Write down what you vendored and from where. The note costs one line and saves the afternoon where somebody has to work out whether the file in the repository or the file upstream is the one that is real.

What this has to do with a blog template

Very little, except that the same reasoning is why this page links to assets/marx.min.css and assets/left.css instead of reaching for a CDN. Two local files, no third-party requests, and a page that renders identically offline.
